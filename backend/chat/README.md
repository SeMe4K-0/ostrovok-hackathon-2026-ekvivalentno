# chat

Модуль чата: Telegram-бот и HTTP API диалога. Часть общего FastAPI-бэкенда, соседний модуль: `agents` (агентный, делает другая часть команды).

Бот ведёт диалог (запрос, уточнения, статус, ответы), а Mini App показывает результат: карту и карточки ([../trip_map](../trip_map/README.md)). Бот присылает кнопку «Открыть карту».

## Как модуль общается с агентами

Модули не импортируют друг друга и не ходят друг к другу по HTTP. Общаются через PostgreSQL и два контракта в [../shared](../shared):

```
Telegram / HTTP ──> chat ──(agent_runs + команда)──> agents
                     ^                                  │
                     └──(chat_events, trip_plans)───────┘
```

**Команды** (`shared/commands.py`) лежат в `agent_runs.command` как JSON и несут только id: историю и план агенты читают из БД сами.

| Команда | Когда |
|---|---|
| `ProcessUserMessage` | новое сообщение пользователя |
| `ProcessClarificationAnswer` | ответ на открытый вопрос (текстом или кнопкой) |

**Что должен делать агентный модуль**

1. Брать из `agent_runs` строки `status='queued'` по `created_at`. **Не больше одного `running` на чат**: сообщения одной поездки обрабатываются строго по очереди. В Postgres брать через `SELECT ... FOR UPDATE SKIP LOCKED`.
2. Ставить `running` / `done` / `failed`. Если нужен ответ пользователя, создать строку в `clarifications` (`question`, необязательные `options` для кнопок, `field`), поставить запуску `waiting_clarification` и выпустить `clarification.required`. Такой запуск очередь не занимает. Ответ придёт новым запуском `ProcessClarificationAnswer`.
3. Писать план в `trip_plans` (`state_json` для себя, `view_json` для карты и карточек) и снимок в `trip_plan_versions`. Чат план только читает: последний `trip_plans` чата и есть текущий.
4. Публиковать события через `shared.events.emit_event(session, chat_id, type, payload, run_id)` **в той же транзакции**, что и данные: событие видно только после коммита.
5. Финальный ответ: строка `chat_messages` (`role='assistant'`, `plan_id`, `plan_revision`) и событие `assistant.message`.

| Событие | Что видит пользователь в Telegram |
|---|---|
| `request.queued` | ставит само chat: «Принял…», с позицией в очереди |
| `agent.progress` | правится одно статусное сообщение, без спама |
| `clarification.required` | вопрос с кнопками (если есть `options`) |
| `plan.updated` | статус «План обновлён (версия N)» |
| `plan.ready` | статусное сообщение убирается |
| `assistant.message` | ответ + кнопка «Открыть карту» |
| `request.failed` | «⚠️ причина», можно повторить |

Модели payload: [shared/events.py](../shared/events.py). Настоящий агентный модуль — `backend/agents` (воркер `python -m agents.runtime.worker`, отдельный сервис в `docker-compose.yml`). Заглушка `DEV_AGENT=true` ([dev_agent.py](dev_agent.py)) нужна только для демо без LLM и **не должна работать одновременно с воркером**: она отвечает демо-планом и один раз задаёт уточняющий вопрос.

## Без дублей и порядок уточнений

Одно входное сообщение даёт не больше одного запуска агентов:

- **Повторная доставка** того же сообщения (тот же `message_id` / `client_message_id`) игнорируется.
- **Двойная отправка**: такой же текст, пока первый ещё `queued` (агенты не начали), в течение 60 секунд игнорируется. Ответ на вопрос двойной отправкой не считается: «Два» на «Гостей?» и на «Номеров?» это два ответа.
- **Один вопрос = один ответ.** Ответы закрывают открытые вопросы по очереди, от старого к новому. Вопрос закрывается атомарным `UPDATE ... WHERE status='open'`, поэтому если два сообщения гонятся за одним вопросом, второе закроет следующий, а при его отсутствии станет обычным запросом.
- Сообщения одного чата принимаются по одному (блокировка строки чата в PostgreSQL), так что позиция в очереди и порядок вопросов не плавают.

Из этого следует требование к агентам: **когда начинаете обработку сообщения, переведите `chat_messages.status` из `queued` в `processing`** (затем `done` / `failed`). Пока статус `queued`, повтор такого же текста считается двойной отправкой.

## Команды бота

| Команда | Что делает |
|---|---|
| `/start` | регистрирует пользователя, приветствие |
| `/plan` | текущий план и кнопка Mini App |
| `/status` | открытый вопрос и число запросов в обработке |
| `/new` | новая поездка (старая сохраняется, её события больше не приходят в чат) |
| `/demo` | готовый демо-план без диалога: `/demo` (Москва и Санкт-Петербург), `/demo japan` (Токио и Осака). Только при `DEV_AGENT=true`; повторный вызов создаёт новую версию того же плана |
| `/help` | подсказка |
| любой текст | запрос агентам, или ответ на открытый вопрос |

Работает только в личных сообщениях. Повторная доставка апдейта Telegram не создаёт второй запрос (дедупликация по `message_id`).

## HTTP API (`/api/v1`)

| Метод и путь | Назначение |
|---|---|
| `POST /auth/telegram` | `initData` Mini App → токен сессии (подпись проверяется токеном бота, `user_id` от клиента не берётся) |
| `GET /chats/active`, `POST /chats` | активный чат; новая поездка |
| `GET/POST /chats/{id}/messages` | история; отправка (202, `client_message_id` для идемпотентности) |
| `POST /chats/{id}/clarifications/{qid}/answers` | ответ на конкретный вопрос (409, если закрыт) |
| `GET /chats/{id}/events` | SSE; продолжение по `?after=` или `Last-Event-ID` |
| `GET /chats/{id}/plan`, `GET /plans/{id}/versions/{rev}` | актуальный план, версия |
| `POST /telegram/webhook` | вебхук бота (проверяется секрет) |

Доступ к чужому чату даёт 404. Токен подписывается `SESSION_SECRET` (или ключом от токена бота).

## Запуск

```bash
cd backend && python3 -m venv ../.venv && source ../.venv/bin/activate
pip install -r requirements-dev.txt
cp ../.env.example ../.env       # токен бота от @BotFather; без Docker нужен ещё воркер агентов или DEV_AGENT=true
uvicorn main:app --port 8080
```

- **Без `TELEGRAM_WEBHOOK_URL`** бот работает через long polling: подходит для локальной разработки, публичный адрес не нужен.
- **С вебхуком** (`TELEGRAM_WEBHOOK_URL=https://<домен>/telegram/webhook`, `TELEGRAM_WEBHOOK_SECRET`) бот регистрирует его при старте. Кнопка Mini App работает только при `PUBLIC_BASE_URL` с **https**; для разработки подойдёт туннель (cloudflared, ngrok). При http в сообщении вместо кнопки будет ссылка.
- **Mini App в Telegram** открывается только по https. Для разработки поднимите туннель на порт приложения и пропишите его адрес:

  ```bash
  ngrok http 8080                     # или cloudflared tunnel --url http://localhost:8080
  # в .env: PUBLIC_BASE_URL=https://<адрес-туннеля>   затем перезапустите приложение
  ```

  После этого в сообщениях бота появится кнопка «Открыть карту» (план конкретной версии), а рядом с полем ввода постоянная кнопка «🗺 Карта» (последний план активной поездки). Карта берёт план из БД по `?plan_id=<uuid>` или `?plan_id=latest`, вход идёт через `initData`, чужие планы недоступны. Без `plan_id` показывается демо-пример (и вне Telegram тоже). Бесплатный ngrok может показывать страницу-предупреждение; если она мешает, используйте cloudflared.
- По умолчанию БД: SQLite-файл `data/dev.db`. Для Postgres: `DATABASE_URL=postgresql+asyncpg://...`, `AUTO_CREATE_TABLES=false` и `alembic upgrade head`.
- Недоступный Telegram или неверный токен при старте не роняют API: ошибка пишется в лог.

Тесты: `pytest` (БД в памяти, Telegram подменён записывающей сессией, токен бота не нужен).

## Что ещё не сделано

- Доставка событий в Telegram рассчитана на **один процесс**. Несколько реплик будут слать дубли: потребуется блокировка или `LISTEN/NOTIFY`.
- Миграции 0001–0003 проверены на PostgreSQL 16 и SQLite (накат, откат, `alembic check`); весь набор тестов проходит на обоих.
- `GET /chats/{id}/events` опрашивает БД раз в секунду. Позже можно заменить на `LISTEN/NOTIFY`.
- Нет отмены запроса из чата и лимитов частоты сообщений.
- Docker: `Dockerfile` и `docker-compose.yml` лежат в корне репозитория (`app` с миграциями при старте, `worker`, `db`).
- Mini App открывает весь веб-интерфейс (`/`: чат, план, карта, корзина); карта читает план из БД (`integration.py`). Запуск с настоящим токеном бота и по HTTPS пока не проверялся.
